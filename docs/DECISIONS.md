## 1. 决策管理规则

重要技术决策使用下列字段记录：

- 编号、日期和状态（Proposed / Accepted / Superseded / Rejected）。
- 背景与约束。
- 备选方案。
- 最终结论和理由。
- 正面与负面影响。
- 需要项目所有者确认的事项。

重大架构变化必须在实现前形成 Proposed 记录，说明迁移、兼容性和回滚影响，并获得项目所有者明确确认后才能标记 Accepted 和实施。重大变化包括核心语言或框架、模块化单体边界、数据库类型、主键/数据口径、公开部署拓扑以及采集执行模型的改变。

## ADR-001：采用 Linux 作为开发和部署基线

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

目标生产环境是 Linux 服务器，项目依赖 Python、Node.js、PostgreSQL 和容器工具，需要开发与生产尽量一致，并能通过命令行自动化复现。

### 备选方案

- Linux 原生开发。
- Windows 原生开发。
- macOS 原生开发。
- Windows/macOS 开发并通过虚拟机或兼容层运行 Linux 工具链。

### 结论

采用 Ubuntu 24.04 LTS 作为主要开发和部署基线。其他操作系统可以作为客户端使用，但必须以 Linux CI/容器验证结果为准。

### 影响

- 优点：开发与生产差异较小；容器、PostgreSQL 和自动化工具生态成熟；LTS 生命周期明确。
- 代价：非 Linux 开发者可能需要虚拟机、WSL 或远程环境；不能假设平台专属命令在所有系统可用。

## ADR-002：后端采用 Python 与 FastAPI

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

平台以数据采集、校验、分析和 REST API 为核心，需要与 Pandas、NumPy、AKShare、SQLAlchemy 和 Pydantic 良好协作，同时提供明确的类型和 OpenAPI 契约。

### 备选方案

- Python + FastAPI。
- Python + Django / Flask。
- Node.js + NestJS。
- C++ Web 框架。

### 结论

采用 Python 3.12 与 FastAPI。业务编排、数据访问和纯计算保持分层，避免把框架对象传播到分析核心。

### 影响

- 优点：数据生态成熟；异步 API 和类型校验支持良好；OpenAPI 文档生成直接。
- 代价：CPU 密集任务需避免阻塞 API；动态语言仍需依赖类型检查、测试和清晰边界保证质量。

## ADR-003：前端采用 Vue 3 与 TypeScript

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版需要搜索、数据状态和 ECharts 金融图表，要求结构清晰、类型安全并兼顾桌面和基础移动浏览。

### 备选方案

- Vue 3 + TypeScript。
- React + TypeScript。
- 服务端模板或无框架 JavaScript。

### 结论

采用 Vue 3、TypeScript 和 Vite，配合 Vue Router、Pinia、Element Plus、ECharts 与 Axios。

### 影响

- 优点：组件模型简洁、渐进式生态成熟、TypeScript 可以约束 API 契约。
- 代价：需要维护 Node 构建链和前后端类型一致性；不能在前端复制后端指标计算。

## ADR-004：持久化采用 PostgreSQL

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

日线数据要求复合主键、外键、检查约束、日期范围查询、事务和幂等 UPSERT，后续还需要可靠备份恢复。

### 备选方案

- PostgreSQL。
- SQLite。
- MySQL/MariaDB。
- 文档数据库或时序数据库。

### 结论

采用 PostgreSQL，使用 SQLAlchemy 2 访问并通过 Alembic 管理 Schema 版本。

### 影响

- 优点：约束、事务、UPSERT、索引和运维工具成熟。
- 代价：本地环境比 SQLite 更重；必须管理连接、migration、备份和恢复。首版数据规模不构成引入专用时序数据库的依据。

## ADR-005：v0.1.0 采用模块化单体而非微服务

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版由小规模团队开发，业务边界仍在验证，预期负载尚无数据。微服务会提前引入服务发现、分布式追踪、部署编排和跨服务一致性成本。

### 备选方案

- 单仓库模块化单体。
- 从第一天拆分 API、采集、指标和用户服务。
- 无明确边界的单体脚本。

### 结论

采用单仓库模块化单体，通过目录、接口和依赖方向隔离模块；API 与调度进程可以独立运行，但共享同一代码库和数据库设计。

### 影响

- 优点：交付、测试、migration 和本地部署简单；事务边界清楚。
- 代价：必须持续执行模块边界检查，防止退化为无分层单体。只有出现经过测量的扩展或组织需求，才评估服务拆分。

## ADR-006：v0.1.0 不使用 C++ 作为主开发语言

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版主要是 Web API、数据库 CRUD、第三方 Python 数据源适配和低频日线分析，不存在已经证实的极端延迟或 CPU 性能瓶颈。

### 备选方案

- Python 作为主语言。
- C++ 实现全部后端和分析。
- Python 主体，在有测量依据时通过独立原生扩展优化热点。

### 结论

使用 Python 作为主开发语言，不以 C++ 构建首版后端。未来只有在 profiling 证明特定纯计算热点无法通过算法、向量化或任务隔离解决时，才提议局部原生优化。

### 影响

- 优点：与金融数据生态直接集成，迭代和测试成本较低。
- 代价：峰值计算性能低于精心优化的 C++；若引入原生扩展，会增加跨平台构建和内存安全风险。

## ADR-007：数据采集使用独立 Worker

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

历史补采和盘后增量更新可能耗时、失败和重试。API 可能启动多个 Worker，若内嵌调度器会重复执行；若在用户请求中同步采集，会导致超时并把第三方不稳定性传给查询链路。

### 备选方案

- 独立 Data Worker 与独立调度进程。
- 在 API 请求中同步采集。
- 在每个 API Worker 内运行调度器。
- 首版引入 Celery、Redis 或 Kafka。

### 结论

采用独立 Data Worker，入口为受控本地 CLI 和独立调度进程；通过 `MarketDataProvider -> Validator -> Repository` 写入本地数据库。首版不引入分布式任务基础设施。

### 影响

- 优点：隔离网络失败和长任务；避免 API 多进程重复调度；查询只依赖本地数据库。
- 代价：需要任务状态、防重、重试、断点和进程运维设计。

## ADR-008：先开发日线研究平台而非实时交易系统

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

目标是个人研究而非交易执行。实时行情、Tick 数据、券商接口和自动下单会显著增加授权、时延、可靠性、资金安全和监管风险。

### 备选方案

- 从历史日线、基础指标和数据质量开始。
- 直接建设实时行情终端。
- 直接接入券商并自动交易。

### 结论

v0.1.0 只做不复权历史日线、K 线、成交量、MA5/20/60 和数据更新状态。实时交易与自动下单明确排除。

### 影响

- 优点：范围可控，可以先验证数据来源、口径、幂等性和研究体验。
- 代价：无法满足盘中监控或交易执行需求；未来扩展必须重新进行数据授权、安全和架构评审。

## ADR-009：M1-04 的 PostgreSQL 驱动与同步任务存储细节

- 日期：2026-10-11
- 状态：Accepted（M1-04 授权范围内的实现细化；无重大架构变更）

### 背景

首个 migration 需要可测试的 PostgreSQL 驱动，以及规划中已要求的任务目标范围、计数、恢复游标和防重约束。

### 备选方案

- psycopg 3 同步驱动或 psycopg2；同步服务现阶段无需引入异步数据库访问链路。
- 明确的范围/计数/游标列或不透明 JSON；防重可以只由应用判断或增加数据库唯一约束。

### 结论

使用 `psycopg[binary]` 3 与 `postgresql+psycopg` URL。任务字段采用类型明确的列，定义见 `PROJECT_PLAN.md` 第 8.5 节。同来源、类型、目标股票和日期区间的 pending/running 任务使用部分唯一索引，并以 `NULLS NOT DISTINCT` 处理全股票/不限日期范围。

### 影响

- 直接支持 UUID、定点数、带时区时间戳和数据库约束的真实集成验收。
- 项目验证基线为 PostgreSQL 16，索引要求 PostgreSQL 15+；降级到更旧数据库需要重新设计。
- 防重仅覆盖完全相同范围；重叠任务协调、过期 running 任务恢复、采集重试和断点推进在 M2/M4 实现。
- 初始 migration 的 downgrade 删除四张业务表，只在一次性测试库验收，不能当作有数据环境的无损回滚。
