## 1. 决策管理规则

重要技术决策使用下列字段记录：

- 编号、日期和状态（Proposed / Accepted / Superseded / Rejected）。
- 背景与约束。
- 备选方案。
- 最终结论和理由。
- 正面与负面影响。
- 需要项目所有者确认的事项。

重大架构变化必须在实现前形成 Proposed 记录，说明迁移、兼容性和回滚影响，并获得项目所有者明确确认后才能标记 Accepted 和实施。重大变化包括核心语言或框架、模块化单体边界、数据库类型、主键/数据口径、公开部署拓扑以及采集执行模型的改变。

## ADR-001：采用 Linux 作为开发和部署基线

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

目标生产环境是 Linux 服务器，项目依赖 Python、Node.js、PostgreSQL 和容器工具，需要开发与生产尽量一致，并能通过命令行自动化复现。

### 备选方案

- Linux 原生开发。
- Windows 原生开发。
- macOS 原生开发。
- Windows/macOS 开发并通过虚拟机或兼容层运行 Linux 工具链。

### 结论

采用 Ubuntu 24.04 LTS 作为主要开发和部署基线。其他操作系统可以作为客户端使用，但必须以 Linux CI/容器验证结果为准。

### 影响

- 优点：开发与生产差异较小；容器、PostgreSQL 和自动化工具生态成熟；LTS 生命周期明确。
- 代价：非 Linux 开发者可能需要虚拟机、WSL 或远程环境；不能假设平台专属命令在所有系统可用。

## ADR-002：后端采用 Python 与 FastAPI

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

平台以数据采集、校验、分析和 REST API 为核心，需要与 Pandas、NumPy、AKShare、SQLAlchemy 和 Pydantic 良好协作，同时提供明确的类型和 OpenAPI 契约。

### 备选方案

- Python + FastAPI。
- Python + Django / Flask。
- Node.js + NestJS。
- C++ Web 框架。

### 结论

采用 Python 3.12 与 FastAPI。业务编排、数据访问和纯计算保持分层，避免把框架对象传播到分析核心。

### 影响

- 优点：数据生态成熟；异步 API 和类型校验支持良好；OpenAPI 文档生成直接。
- 代价：CPU 密集任务需避免阻塞 API；动态语言仍需依赖类型检查、测试和清晰边界保证质量。

## ADR-003：前端采用 Vue 3 与 TypeScript

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版需要搜索、数据状态和 ECharts 金融图表，要求结构清晰、类型安全并兼顾桌面和基础移动浏览。

### 备选方案

- Vue 3 + TypeScript。
- React + TypeScript。
- 服务端模板或无框架 JavaScript。

### 结论

采用 Vue 3、TypeScript 和 Vite，配合 Vue Router、Pinia、Element Plus、ECharts 与 Axios。

### 影响

- 优点：组件模型简洁、渐进式生态成熟、TypeScript 可以约束 API 契约。
- 代价：需要维护 Node 构建链和前后端类型一致性；不能在前端复制后端指标计算。

## ADR-004：持久化采用 PostgreSQL

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

日线数据要求复合主键、外键、检查约束、日期范围查询、事务和幂等 UPSERT，后续还需要可靠备份恢复。

### 备选方案

- PostgreSQL。
- SQLite。
- MySQL/MariaDB。
- 文档数据库或时序数据库。

### 结论

采用 PostgreSQL，使用 SQLAlchemy 2 访问并通过 Alembic 管理 Schema 版本。

### 影响

- 优点：约束、事务、UPSERT、索引和运维工具成熟。
- 代价：本地环境比 SQLite 更重；必须管理连接、migration、备份和恢复。首版数据规模不构成引入专用时序数据库的依据。

## ADR-005：v0.1.0 采用模块化单体而非微服务

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版由小规模团队开发，业务边界仍在验证，预期负载尚无数据。微服务会提前引入服务发现、分布式追踪、部署编排和跨服务一致性成本。

### 备选方案

- 单仓库模块化单体。
- 从第一天拆分 API、采集、指标和用户服务。
- 无明确边界的单体脚本。

### 结论

采用单仓库模块化单体，通过目录、接口和依赖方向隔离模块；API 与调度进程可以独立运行，但共享同一代码库和数据库设计。

### 影响

- 优点：交付、测试、migration 和本地部署简单；事务边界清楚。
- 代价：必须持续执行模块边界检查，防止退化为无分层单体。只有出现经过测量的扩展或组织需求，才评估服务拆分。

## ADR-006：v0.1.0 不使用 C++ 作为主开发语言

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

首版主要是 Web API、数据库 CRUD、第三方 Python 数据源适配和低频日线分析，不存在已经证实的极端延迟或 CPU 性能瓶颈。

### 备选方案

- Python 作为主语言。
- C++ 实现全部后端和分析。
- Python 主体，在有测量依据时通过独立原生扩展优化热点。

### 结论

使用 Python 作为主开发语言，不以 C++ 构建首版后端。未来只有在 profiling 证明特定纯计算热点无法通过算法、向量化或任务隔离解决时，才提议局部原生优化。

### 影响

- 优点：与金融数据生态直接集成，迭代和测试成本较低。
- 代价：峰值计算性能低于精心优化的 C++；若引入原生扩展，会增加跨平台构建和内存安全风险。

## ADR-007：数据采集使用独立 Worker

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

历史补采和盘后增量更新可能耗时、失败和重试。API 可能启动多个 Worker，若内嵌调度器会重复执行；若在用户请求中同步采集，会导致超时并把第三方不稳定性传给查询链路。

### 备选方案

- 独立 Data Worker 与独立调度进程。
- 在 API 请求中同步采集。
- 在每个 API Worker 内运行调度器。
- 首版引入 Celery、Redis 或 Kafka。

### 结论

采用独立 Data Worker，入口为受控本地 CLI 和独立调度进程；通过 `MarketDataProvider -> Validator -> Repository` 写入本地数据库。首版不引入分布式任务基础设施。

### 影响

- 优点：隔离网络失败和长任务；避免 API 多进程重复调度；查询只依赖本地数据库。
- 代价：需要任务状态、防重、重试、断点和进程运维设计。

## ADR-008：先开发日线研究平台而非实时交易系统

- 日期：2026-10-10
- 状态：Accepted（项目初始基线）

### 背景

目标是个人研究而非交易执行。实时行情、Tick 数据、券商接口和自动下单会显著增加授权、时延、可靠性、资金安全和监管风险。

### 备选方案

- 从历史日线、基础指标和数据质量开始。
- 直接建设实时行情终端。
- 直接接入券商并自动交易。

### 结论

v0.1.0 只做不复权历史日线、K 线、成交量、MA5/20/60 和数据更新状态。实时交易与自动下单明确排除。

### 影响

- 优点：范围可控，可以先验证数据来源、口径、幂等性和研究体验。
- 代价：无法满足盘中监控或交易执行需求；未来扩展必须重新进行数据授权、安全和架构评审。

## ADR-009：M1-04 的 PostgreSQL 驱动与同步任务存储细节

- 日期：2026-10-11
- 状态：Accepted（M1-04 授权范围内的实现细化；无重大架构变更）

### 背景

首个 migration 需要可测试的 PostgreSQL 驱动，以及规划中已要求的任务目标范围、计数、恢复游标和防重约束。

### 备选方案

- psycopg 3 同步驱动或 psycopg2；同步服务现阶段无需引入异步数据库访问链路。
- 明确的范围/计数/游标列或不透明 JSON；防重可以只由应用判断或增加数据库唯一约束。

### 结论

使用 `psycopg[binary]` 3 与 `postgresql+psycopg` URL。任务字段采用类型明确的列，定义见 `PROJECT_PLAN.md` 第 8.5 节。同来源、类型、目标股票和日期区间的 pending/running 任务使用部分唯一索引，并以 `NULLS NOT DISTINCT` 处理全股票/不限日期范围。

### 影响

- 直接支持 UUID、定点数、带时区时间戳和数据库约束的真实集成验收。
- 项目验证基线为 PostgreSQL 16，索引要求 PostgreSQL 15+；降级到更旧数据库需要重新设计。
- 防重仅覆盖完全相同范围；重叠任务协调、过期 running 任务恢复、采集重试和断点推进在 M2/M4 实现。
- 初始 migration 的 downgrade 删除四张业务表，只在一次性测试库验收，不能当作有数据环境的无损回滚。

## ADR-010：M1-05 本地开发 Compose 的网络与迁移边界

- 日期：2026-10-11
- 状态：Accepted（M1-05 授权范围内的实现细化）

### 背景

已有 API 健康接口、Vue 开发壳和初始 migration，需要可复现的本地容器环境，并能分别验证进程健康、实际数据库连接和迁移状态。

### 备选方案

- 只容器化 PostgreSQL，其余服务原生运行。
- 同时提供 `db`、`api`、`web` 开发容器，源代码只读挂载支持热更新。
- 在 API 启动命令中隐式迁移，或使用显式 Alembic 操作。

### 结论

采用三服务本地 Compose，并保留原生开发命令。使用项目隔离卷、服务名 DNS、本机端口绑定、数据库健康依赖和显式迁移。数据库凭据通过 PG* 环境变量传递，URL 不包含密码。Vite 提供同源 `/api` 代理；不增加 Worker/Scheduler 业务。

### 影响

- 可以独立证明数据库可用、API 进程存活和前端 HTTP 转发。
- 现有数据卷不会被普通停止/重启删除；更改环境密码不会自动更新卷内账户。
- 开发镜像包含测试依赖与热更新，不属于生产发布方案。
- Docker Hub 网络访问需要 daemon 的有效网络配置或从官方源下载并导入镜像；不能提交本机代理或关闭 TLS 验证来规避。
- 镜像固定主版本与发行版但未固定 digest，后端依赖尚无锁文件；生产可复现性将在 M5 评估并进一步固定。

## ADR-011：M1-06 配置隔离与安全 HTTP 运行基础

- 日期：2026-10-11
- 状态：Accepted（M1-06 授权范围内的实现细化，不改变核心架构）

### 背景

本地三服务已可运行，需要避免测试误连开发库，统一 HTTP 错误和关联 ID，并防止原始请求或异常中的凭据进入日志。

### 备选方案

- 引入额外配置/日志依赖，或使用已有 Pydantic 和 Python 标准 logging。
- 自动加载开发 `.env` 并复用数据库配置，或显式环境白名单与独立测试 URL。
- 原样转发框架异常消息/访问日志，或统一公开错误和受控诊断字段。

### 结论

采用已有依赖；Python 不自动读取 `.env`、不缓存全局配置。test 模式只接受 `TEST_DATABASE_URL`，不回退开发库；migration fixture 额外要求新建空 `*_migration_test`。保留 PG* 和无密码 URL 兼容性，不隐式迁移。使用纯 ASGI 中间件生成服务端 ID、统一错误模型和应用命名空间 JSON 日志；框架 HTTP/校验异常使用自定义 handler（参见 [FastAPI 官方说明](https://fastapi.tiangolo.com/tutorial/handling-errors/)）。

### 影响

- 健康成功响应不变，所有响应增加 `X-Request-ID`；调用者 ID 不回显。
- 不新增业务接口、表、migration、Worker/Scheduler 或依赖，不改变 API 分层。
- 日志只记录路由模板、状态、耗时和安全诊断位置；不保存原始请求内容或异常消息。禁用 Uvicorn 原始 access log。
- JSON formatter 脱敏凭据/连接串；输出流失效仅报固定安全提示，避免标准 logging 的异常转储泄漏原始记录。
- 原始异常文本缺失会降低诊断细节，需要结合关联 ID、异常类型、代码位置及受控复现排查；不能为方便排查重新加入未审查的原文。
- 仅管理应用日志，不声称第三方库日志已全部净化；未来接入 Provider 时必须审查第三方日志与重试。生产访问控制、轮转和监控仍待后续阶段。

## ADR-012：M2-01 Provider 数据契约与 SDK 调用隔离

- 日期：2026-10-11
- 状态：Accepted（已批准 M2-01 范围内的实现细化，无核心架构或数据口径变更）

### 背景

需落实可替换 Provider，避免 AKShare 字段/Pandas 进入服务层；官方基础列表包含北京市场且没有 timeout，日线成交量使用手。当前数据库和产品首版只支持 SH/SZ、不复权、人民币元与股。

### 备选方案

- 将上游 DataFrame 传入服务层，或返回统一不可变 DTO 与含来源/时间/单位的批次。
- 使用不可取消的线程限制等待，或用标准库子进程限制整次 SDK 调用并在超时后终止/回收。
- 为 API 强制安装 SDK，或提供已批准数据源的可选依赖 extra。

### 结论

选择 Protocol、不可变 dataclass 与批次元数据；AKShare 1.19.1 放在 market-data extra。基础信息使用 stock_info_a_code_name，显式排除范围外北京证券并记录数量；未知上市日期/状态为 None/unknown。日线使用 stock_zh_a_hist，固定 daily、adjust=""，成交量手转股、金额元。使用私有单次 SDK 子进程，总超时复用 Settings；错误复用 ApplicationError，日志复用 stockinsight 安全命名空间。SDK 原始输出/异常不转发。

### 影响

- 不新增业务 Router、表、migration、采集 CLI 或调度服务，架构调用方向不变；现有 API 镜像不安装可选 SDK。
- 批次来源/时间/复权必须在后续持久化时附到每条日线；空批次仍保留元数据，不表示业务采集完成。
- 子进程有导入开销，吞吐需后续实测；总超时覆盖 SDK 内部多次请求。Provider 不自动重试，批次退避/恢复留到 M2-05。
- 字段/类型/单位可表示性检查属于适配边界；OHLC、负值、去重、日历和异常量级等完整业务 Validator 留到 M2-02。
- 测试只使用明确标记的模拟 fixture/fake SDK。真实网络稳定性、样本和授权仍未验收；传递依赖锁定继续留到 M5。详见 [Provider 专题](MARKET_DATA_PROVIDER.md)。

## ADR-013：M2-02 确定性校验与精确存储边界

- 日期：2026-10-11
- 状态：Accepted（已批准 M2-02 范围内的实现细化；无架构、Schema 或价格口径变更）

### 背景

M2-01 已完成上游映射，内部 DTO 仍可能包含错误的代码、重复日期、非法 OHLC 或 PostgreSQL 会隐式舍入/溢出的值。交易日历来源和市场统计异常阈值尚未批准，不能用任意固定值替代。

### 备选方案

- 在 Provider/Repository 内混合业务规则，或用独立纯函数 Validator。
- 依赖数据库自动舍入和覆盖重复，或预先拒绝不精确数值和重复行。
- 隐式联网获取交易日历，或显式注入已确认日历并说明缺省边界。

### 结论

复用 MarketDataBatch/StockInfo/DailyBar，使用标准库纯函数校验并返回排序的新不可变批次；代码支持范围、字段规则见 [Validator 专题](MARKET_DATA_VALIDATOR.md)。只规范化显式代码的大小写/外围空白，不猜市场或补零。来源/接口/单位保持原值，aware 时间转 UTC 保留同一时刻；future 日期比较以批次时间对应的上海业务日期为准，不读取当前时钟。

按既有 numeric(18,4)/numeric(24,2)/BigInt 约束检查，拒绝溢出、非有限值、负量、非法 OHLC 和会改变数值的舍入。Decimal 精度检查不依赖 ambient context；只移除数值不变的冗余尾零/零 exponent。Provider 手转股只执行一次。空批次可合法返回，不代表采集完成；任何非法行令本次批次校验失败，保留输入，后续任务编排再处理跨股票部分失败。

### 影响

- 不引入依赖、网络、Web/ORM、数据库变更、API、CLI 或调度器；已有 Provider/模型保持不变。
- 日历以 date set/frozenset 显式传入；未提供时只能做周末/范围检查，不声明节假日、临时休市或区间完整性验收。
- 不虚构市场量级/涨跌幅阈值，不从代码证明真实上市状态；unknown 状态与缺失上市日期保留，后续同步不能据此覆盖已确认信息。
- 错误只携带固定规则/字段/行号；不输出原始值。未来任务层需捕获并通过既有安全日志与任务状态报告，不将纯 Validator 接到 HTTP 请求采集链路。
- 原有数据库非负规则允许零 OHLCV；不增加未经批准的严格正值或量额一致性策略。

## 2. 新决策模板

```markdown

- 状态：Proposed

说明问题、约束和触发原因。

- 方案 B

记录选择及理由；未确认前不得提前实施重大变化。
```
