## 2. 当前实测基线

以下为本轮实测，历史验收另见 [M5](M5_ACCEPTANCE.md)；并未把 M5 性能数据直接沿用为本轮结果。

- db/API/web healthy，scheduler running。宿主发布仍只有 `127.0.0.1:5432/8000/5173`；没有改动原库/卷、来源设置或服务配置。
- PostgreSQL 16，revision `0001_initial_schema`；`pg_database_size` = **9,247,767 bytes（8.82 MiB）**。
- 5,223 只目录股票；行情仅 4 只、2026-01-05～10-09，日线/指标各 732 行；同步任务 14 行。

| 表 | 行数 | `pg_total_relation_size`（bytes，含索引/TOAST） |
| --- | ---: | ---: |
| stocks | 5,223 | 868,352 |
| daily_prices | 732 | 196,608 |
| technical_indicators | 732 | 221,184 |
| data_sync_jobs | 14 | 81,920 |

尺寸读取在 `BEGIN READ ONLY` 中执行，设置 10 秒 statement timeout。数据库体积包含目录/系统对象等，不包含整个实例的 WAL、其他数据库、Docker 镜像或备份。函数口径见 [PostgreSQL 16 官方说明](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADMIN-DBSIZE)。

资源单次快照：db 207.4 MiB、API 95.26 MiB、Vite web 200.9 MiB、scheduler 68.15 MiB，总计约 **572 MiB**。这是任务空闲时 Docker stats 用量，**不是采集峰值或生产最低内存**。宿主为 4 个可见逻辑 CPU、约 7.76 GiB 内存、8 GiB swap，且有其他进程；未限定为 2 核/4 GiB。当前 Compose 未配置资源上限；Docker 默认不限制容器资源，见 [官方说明](https://docs.docker.com/engine/containers/resource_constraints/)。

当前数据库参数：shared_buffers 128 MiB、work_mem 4 MiB、max_connections 100、max_wal_size 1 GiB。work_mem 不能当成每实例总上限；生产连接池/并行操作需共同计入预算。本轮未调整参数。

### 查询样本

复现命令（服务运行时，从仓库根目录执行）：

```bash
.venv/bin/python scripts/benchmark_queries.py
```

脚本固定 loopback API，禁用环境代理/重定向，只调用搜索、183 条日线、183 条均线和任务状态 GET；每档 4 次预热及 80 次测量，共 240 次测量全部成功。每个接口每档只有 20 个样本；p95 用 nearest-rank，排除预热。

| 同时在途请求 | 成功请求/秒（四接口等比例） | 搜索 p95 ms | 日线 p95 ms | 均线 p95 ms | 状态 p95 ms |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 41.82 | 28.51 | 36.54 | 26.56 | 20.80 |
| 4 | 59.16 | 85.25 | 84.85 | 90.42 | 84.50 |
| 10 | 63.65 | 200.11 | 210.52 | 200.38 | 192.29 |

没有用户思考时间、没有 TLS/反向代理/公网 RTT；为开发 Uvicorn reload、热缓存、单股重复查询、几秒钟短样本，未与采集高峰叠加。10 个在途请求不等于 10 名用户的全部页面流量，更不证明 100 只或多年历史上的容量。详情页会发起多个请求，生产验收还应覆盖 10 人同时打开页面的突发。

日线响应约 48,342 bytes、指标约 49,284 bytes。假设每人每天 100 次详情、10 人、每次主要数据约 100 KB，则约 3 GB/月 API 数据量；这是手算情景，未包含静态资源、协议、状态轮询、重试和备份流量，计费时应预留至少数倍余量。当前详情 chunk 约 604 KB（gzip 208 KB）为上轮构建记录；本轮未重建，不能作为公网首屏验收。

### 采集与备份样本

只读查看现有任务：4 个成功 incremental 历史耗时 1.144～2.555 秒；成功 backfill 1.104～2.889 秒；股票目录 full 为 21.728 秒。失败历史保留，其中最长 18.096 秒。它们来自原 4 股/原来源与小历史范围，**未实测 100 股批次、当前优先源备用延迟或目标区域网络**。

本轮将 `pg_dump -Fc --no-owner --no-acl` 输出到内存后丢弃：**92,383 bytes、0.347 秒**（含 Docker exec 启动）；未落盘明文、未做恢复。已有加密归档约 81 KiB。M5 独立恢复已通过内容/Schema/API 核对，但没有生产异地传输耗时或计时 RTO，不能据此宣称达到 2 小时目标。

本轮 JSON 证据在 `data/acceptance/m6-20261012/`（Git 忽略）：`query-benchmark.json`、`backup-sample.json`。表格/参数/资源快照记录在本报告；不提交数据库、备份或真实凭据。

## 3. 存储增长估算

当前一对“日线+一个版本均线”含索引均摊约 `(196608+221184)/732 = 570.75 bytes`。小表存在固定页分配，先用 **1 KiB/对** 做规划，再为活跃库预留 2 倍空间；这不是大库实测，也不包含多指标版本、任务、WAL或备份。

采用今年受控日历 242 日/年作情景系数，未来年份需另行核验，不以此生成交易日历。停牌/上市日期会减少实际行数，股票数量变化会改变结果。

| 场景 | 预计日线行数（指标同数） | 1 KiB/对的基础体积 |
| --- | ---: | ---: |
| 4 只 × 1 年 | 968 | 0.95 MiB |
| **首期：100 只 × 1 年** | **24,200** | **23.63 MiB** |
| 扩展：100 只 × 5 年 | 121,000 | 0.115 GiB |
| 对照：5,223 只 × 5 年 | 6,319,830 | 6.03 GiB |
| 对照：5,223 只 × 10 年 | 12,639,660 | 12.05 GiB |

任务表也随每股每日增长。100 只一年约 24,200 项，5,223 只一年约 1,263,966 项；可先以 1 KiB/任务规划约 24 MiB/年或 1.21 GiB/年，但当前 14 行不足以实测单位成本。失败/补采会额外增长；任务成功记录参与调度持久防重，**不得为了轮转日志直接删除历史任务**，归档需单独设计。

首期 80 GiB 磁盘的规划分配：系统/当前及上版镜像 15、活跃数据库 20、WAL/临时空间 10、轮转日志 5、本机短期加密备份 5、空闲 25 GiB。各项是预算分配，不是当前占用。备份最终按实际 dump 大小 × 保留份数 + 失败重试空间计费；异地副本另计，不把同盘副本当故障隔离。大批 backfill 及旧镜像清理必须先看空闲空间。

## 4. 采集能力比存储更需验证

源代码证据：

- [Scheduler.tick](../backend/app/jobs/scheduler.py) 在所有权锁下 `for symbol in self.symbols` 串行执行。
- [RetryPolicy](../backend/app/jobs/collection.py) 默认 3 次尝试、1/2 秒退避；[PolicyProvider](../backend/app/collectors/source_policy.py) 在优先模式可先东方财富再腾讯；现有 Compose 单源请求 timeout 120 秒。
- [IndicatorService](../backend/app/services/indicators.py) / [IndicatorRepository.closes](../backend/app/repositories/indicators.py) 每股读取全历史收盘价重算；行情与指标同事务，重叠未变化指标不重写。增长后的 CPU/内存仍需测量。

若成功单股保持 1.144～2.555 秒，100 股约 1.9～4.3 分钟；但只要每股优先源先等待完整 120 秒再备用，100 股仅优先源等待就达 **3 小时 20 分钟**。全市场同情景为 **174.1 小时**，还未计备用、重试、写入和指标。此为机制推演，不是上游必然超时或容量上限。

首期不通过增加 API worker 数来解决采集串行或上游限流，也不擅自并行爬取。目标区域需测东方财富/腾讯的实际可达性、成功率与 timeout/fallback；根据观测确认显式策略和超时。约 100 只扩展先做 10→30→100 股受控验证，关注每阶段成功率、耗时和存储，再决定调整；本轮未联网新增采集或写入名单。

## 5. 规格、区域、成本与域名提案

**首期候选：2 vCPU、4 GiB RAM、80 GiB 可扩容 SSD，单机 Linux Compose。** 这是供目标环境验证的起点，与既定模块化单体部署形态一致。当前样本不足以保证 100 股并发采集/查询负载，购买前仍需第7节门禁。

运行内存的暂定预算：系统/Docker 512 MiB、PostgreSQL 1,024 MiB、单 API 进程 512 MiB、单 scheduler（含 SDK 子进程）1,280 MiB、静态代理128 MiB、轻量监控128 MiB、余量512 MiB，共4 GiB。采集部分未经峰值采样，不能直接照此设置硬限制；先做限定资源演练，按真实 working set 调整。前端在 CI/本地构建静态产物，VPS 不常驻 Vite/Node 构建服务。

2–10 人首期从一个 API worker 测起；增加 worker 前核算每进程 SQLAlchemy Engine 连接池及数据库连接预算，不能只扩大 PostgreSQL max_connections。生产代理/备份/峰值使余量不足，或新增多年/全市场范围时，再评估 **4 vCPU / 8 GiB / 160 GiB**；暂不购买更大实例。

### 区域

先比较靠近实际受邀用户的区域；若用户主要在中国大陆，可把香港/新加坡作为网络评估候选，不承诺任何供应商在那里有对应套餐。必须同时测：用户→HTTPS 页面延迟、VPS→两个上游可达性/速率、备份→独立存储传输；不能只看 ping。大陆区域仅在用户选定供应商并确认相应上线要求后评估，不在本轮作法律结论。既有代理凭据不得复制进镜像或日志。

不依赖 `/health` 独自判定业务就绪：它仅证明进程存活。生产需另测数据库只读查询、完整页面和最新已收盘目标日行情。2026 日历覆盖至12-31，提前30天提示后续受控日历更新，不推算未来工作日。

## 7. 目标环境验收与扩容触发

以下均为**建议目标、未验收**：

1. 先在隔离环境以2 vCPU/4 GiB、生产镜像/代理、与首期相符的100股/历史量运行；数据只写隔离库，保留原4股库与卷。采集扩展须用户确定名单/起点与许可后执行。
2. 10人页面突发（含详情多请求）、持续15分钟、采集与备份叠加；API服务端p95≤500ms、失败率<1%、无OOM/连接耗尽。用户网络/浏览器首屏另测，不能用loopback替代。覆盖宽搜索、最大1000条、不同股票、冷/热缓存。
3. 100股正常盘后批次建议30分钟内完成；记录备用/重试场景耗时，目标日缺行显式可见。每日18:30上海时间仍未达到最新已收盘目标日则告警；停牌等失败有明确信息，不伪造数据。
4. 持续内存使用超过80%、swap抖动、CPU长时超过70%且延迟超标，先定位进程/查询/来源；确有资源瓶颈再升4核8GiB。上游timeout优先解决来源可达性，不能仅扩CPU。
5. 磁盘70%告警、80%限制非必要大批补采；备份超过26小时未成功告警。恢复到独立实例核对内容/Schema/API，并计时验证提议RPO/RTO。实例WAL、任务和镜像也需测量，不能只盯业务表。

## 8. 结论与下一步

M6-01 已交付可复现基线、100股存储模型、查询短样本、候选规格/费用及生产缺口。评估支持继续准备小规模受邀预览，**不构成已批准采购或生产容量承诺**。

下一步先确认 ADR-022、预算、访问地域/域名、100股名单及历史起点、数据用途许可与恢复目标；按确认内容进入 M6-02/03，在本地或隔离环境完成可审阅的生产配置和演练，再经 M6-04 明确授权采购/部署。当前无需购买服务器。
